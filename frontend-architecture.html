Mugloar game client architecture

A browser client for playing Dragons of Mugloar yourself. It shows the jobs board with odds and recommendations, the shop, your stats, reputation and an activity log. There is no server of our own: the browser talks straight to the public API, and all game logic runs in the browser.

Layers

The code is layered by type, using the create-vue default folders plus one pure-logic layer, game/. Imports only go in the direction of the arrows. ESLint enforces this per folder, so a component that imports the store, or game logic that imports Vue, fails the lint.

Talking to the API

The browser calls https://dragonsofmugloar.com/api/v2 directly; the API allows cross-origin requests, so there is no proxy and no backend of our own. No key or login is needed. Every request goes through one function in api/client.ts.

ReputationPOST /:gameId/investigate/reputationyesThe player asks around
  • Raw in, decoded out. api/ returns DTOs exactly as the API sends them. The store runs every ad through game/decodeAd() before storing it, so nothing past the store sees an encrypted ad.
  • One error shape. Any failure becomes ApiError with kind not-found, network or http. Error bodies are never parsed, because the API answers errors with HTML. The store maps errors to state; components never catch.
  • Only the board decides expiry. A 404 from GET messages means the game is gone, and the player returns to the start screen with a notice. A 404 from solve, buy or the shop only shows an error; the next board read decides.
  • Retries. Only the board read retries on its own, after 2 s and then 5 s. Solve, buy and reputation are never retried, because a retry could take a second turn. While the board can't be refreshed, solving is blocked and a "Check the board again" button appears.
  • One request at a time. While an action is pending, every action control is disabled. A buy you can't afford is disabled too, since a failed buy still costs a turn.
  • Stale responses are dropped. Each action remembers its game id. If you start another game while a response is in flight, that response changes nothing.
  • API text is untrusted. Ad text is rendered as text, never as HTML.

State

useGameStore is the single owner of the game. State changes only inside its actions: start, load, solve, buy, investigateReputation, and the two retries refreshMessages and refreshShop.

StateMeaning
gameId, statusThe game, and one of idle, loading, playing, over, expired
statsLives, gold, level, score, turn. Each can be unknown: after a reload the API has no way to read them until the next turn.
board, boardStaleDecoded ads, and whether the last refresh failed
shop, reputationItems for sale, and the latest reputation reading
logOne TurnRecord per turn, in memory for this game
purchases, stateEstimateBuys per item and the estimated state reputation; they feed the recommendations
pending, errorThe one-request guard, and the last error
rankedJobs, recommendedItem, shopHintComputed from the state above with game/ functions. Views read these; they never rank anything themselves.

Solve, buy and reputation share one pipeline: guard, snapshot, call, merge, log, game-over check, board refresh. The game loop doc walks through it.

  • The URL picks the game. GameView loads the game named in the URL once. Switching between jobs and shop never reloads it, and a link to a game opens that game.
  • One shell. GameView renders the stats bar, reputation, the jobs/shop tabs and the activity log; the active panel renders in its <RouterView>.
  • Layout. On desktop the page fits the window and only the panel and the log scroll. On phones the page scrolls, with the stats bar and the log pinned.
  • Accessibility. Focus moves to the new heading on each route change, and back to the panel heading when a turn disables the control you used. The log is one live region, so screen readers hear each result once. Icons stay visible in forced-colors mode. Sizes are in rem.

Recommendations

The hints come from the same decision tree the bot plays with, ported to TypeScript in game/recommendations.ts. A job's value is win % × reward − loss % × (75 + best safe reward). Bait ads are flagged as traps, steals are flagged when they would sink your standing with the state, and the shop tab says "Low on lives" or "Level up" when the tree would buy. Nothing is hidden or disabled; the player always decides. The rules and their evidence are in the backend doc.

Quality gates

  • Tests: Vitest with jsdom covers the game logic, the store pipeline and the components. Tests stub fetch and never call the live API.
  • Types: vue-tsc runs as part of pnpm build.
  • Lint: oxlint (correctness rules, plus braces on every if) and ESLint (Vue rules and the layer boundaries above).
