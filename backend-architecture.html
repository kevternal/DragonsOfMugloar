Mugloar NPC architecture

A console app that plays Dragons of Mugloar on its own. It starts a game, picks a move every turn with a fixed decision tree, and keeps going until the dragon dies. It is not a server: it has no HTTP endpoints, and the browser client does not use it.

How it runs

Spring Boot starts without a web server. Spring wires the parts together in NpcConfig, then NpcRunner calls GamePlayer.play() once. When that game ends, the app exits.

Architecture

Dependencies point inward to game/, which has no Spring and no I/O, so the decision tree and the game state are unit-tested with plain data. GamePlayer is the only class that talks to both the API and the game state. It reports through the GameEvents port, so the console and the history file are two views of the same events, and neither knows about the other.

Talking to the API

MugloarClient wraps Spring's RestClient. It sends its own User-Agent, because the API rejects some default ones. Every call goes through one send(), which turns any failure into a MugloarApiException.

CallEndpointRetriedA 404 means
start()POST /game/startnoerror
shop()GET /:gameId/shopnoerror
messages()GET /:gameId/messagesafter 2 s and 5 s, on network errors, 5xx and 429EXPIRED: the game is over or gone
solve()POST /:gameId/solve/:adIdnever: a retry could take a second turnGONE: the ad has expired
buy()POST /:gameId/shop/buy/:itemIdnever: a failed buy still takes a turnGONE: the item is gone
  • No reputation calls. Asking for reputation costs a turn, so the NPC keeps its own estimate instead: steal −2, infiltrate +2, investigate +1 per successful solve.
  • After a GONE: the player remembers the dead ad or item, reads the board once more and decides again. If that read fails or leaves nothing to play, the NPC ends the game itself.
  • No request spacing or budget. Requests go out as fast as the server answers. The summary prints how many were sent.
  • Tests never call the live API. HTTP is mocked, and clocks and sleeps are injected.

The full turn-by-turn flow, and how it differs from the browser client, is in the game loop doc.

Decision tree

Each label maps to a tier, and to a win rate measured over thousands of live solves:

TierLabel and win rate
SafeSure thing 1.00 · Piece of cake 0.95
ModerateWalk in the park 0.87 · Quite likely 0.72 · Hmmm.... 0.63
RiskyGamble 0.55 · Risky 0.41 · Rather detrimental 0.37
DeadlyPlaying with fire 0.31 · Suicide mission 0.06 · Impossible 0.00

In the tree, safe means a Safe-tier label and deadly a Deadly-tier label. Every turn the tree runs from top to bottom, and the first rule that matches decides the move:

flowchart TD
  b(["Board"]) --> f1["Drop bait ads<br/>Steal super awesome diamond …"]
  f1 --> f2{"Would a steal push state<br/>reputation below −8, or is<br/>bait already showing?"}
  f2 -- yes --> f2a["Also drop steals<br/>unless nothing else is left"]
  f2 -- no --> r1
  f2a --> r1{"1 life and a<br/>potion affordable?"}
  r1 -- yes --> heal["Buy healing potion"]
  r1 -- no --> r2{"2 lives and<br/>no safe ad?"}
  r2 -- "gold ≥ 350" --> w2["Buy a +2 item"]
  r2 -- "no, or less gold" --> r3{"2+ lives, gold ≥ 400,<br/>and not every ad safe?"}
  r3 -- yes --> lvl["Buy a +2 item<br/>least bought of the five"]
  r3 -- no --> r4{"Every ad deadly<br/>and 2+ lives?"}
  r4 -- "gold ≥ 350" --> lvl2["Buy a +2 item"]
  r4 -- "no, or less gold" --> r5{"Gold below<br/>a potion?"}
  r5 -- yes --> safest["Solve the lowest-tier ad,<br/>then highest reward"]
  r5 -- no --> best["Solve the best-value ad<br/>win rate × reward −<br/>loss rate × loss cost"]
  • Why heal only at 1 life: a potion costs 50 gold and a turn. At 2 lives a level item is the better buy, since it makes ads easier instead of just adding a buffer.
  • Why it levels so hard: levels are the only thing that makes labels easier, and difficulty rises every turn. Gold has no value at game over, so anything above a small potion reserve goes into +2 items.
  • Why it stops levelling once every ad is safe: those levels would change nothing, so every turn becomes a solve and the score grows fastest.
  • Why the loss cost: a loss costs a potion and a turn to buy it. The loss cost is 75 plus the best safe reward on the board, which is what that turn would otherwise have earned. It keeps long shots from beating solid jobs: a 63% job paying 70 beats a 31% job paying 200. Of the bases tried (50, 65, 75, 100), 75 played best: lower took too many risks, and 100 slowed income.
  • Why only +2 items: a +1 item eases about 3% of ads but costs a whole turn. Every losing test game bought piles of them, and the best games bought almost none.
  • Why skip bait and limit steals: bait always fails. Steals succeed, but each one lowers the state reputation by 2, and bait starts showing up once state falls to about −10. Stopping steals at −8 keeps bait off the board. Infiltrate (+2) and investigate (+1) jobs raise state back up.

The browser client shows the same tree as hints: it ranks jobs by this value and marks the item the tree would buy. See the frontend doc.
